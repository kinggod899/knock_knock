## 关键结论：为什么键鼠曾经「不可用」

**这是本次最大的教训，也是第一版走错方向的根因。**

第一版在独立 python 进程里测输入，结论是「游戏屏蔽一切外部注入」：
pynput 键盘无反应、SendInput 无反应、PostMessage 报拒绝访问、SetCursorPos 拒绝访问。
于是改用 vgamepad 虚拟手柄（内核级设备，绕过限制）「成功」了。

**那个结论错在测试姿势。** 真相：

- 绝区零进程是**提权运行**的（实测 `TokenIsElevated=1`）。
- Windows UIPI：低权限进程的输入事件到不了高权限窗口。我的 DSH 子进程是
  `IsUserAnAdmin=0`，所以发什么都被吃掉。
- 提权之后重测，**pynput 的 keyboard/mouse 直接就能驱动游戏**。
- 一条龙启动器本来就用 pyuac 提权（`src/one_dragon/launcher/exe_launcher.py`
  里 `if not pyuac.isUserAdmin(): pyuac.runAsAdmin(...)`），插件跑在框架里天然有权限。

所以：**验证输入通路时，必须先对齐目标进程的权限级别**，否则得出的「平台不支持」
结论完全是假的。

## 流程第 0 步：传送到录像店

knock knock 只能在**录像店范围内**打开，所以每次跑之前先传送。

复用框架的 `Transport`（录像店营业、情报板那些应用用的都是这一套）：

```python
op = Transport(self.ctx, '录像店', '房间')
return self.round_by_op_result(op.execute())
```

目的地用「房间」——和贝果计划、情报板一致。录像店可选点位（`assets/game_data/map_area.yml`）：

```
HDD / 影像档案架 / 柜台 / 房间 / 车库
```

`Transport` 内部会处理「当前不在大世界 / 停在地图页 / 在战斗中」等各种情况，
比自己写一遍稳。

节点顺序（`is_start_node` 是传送）：

```
传送到录像店 -> 唤出 knock knock -> 清理过期邀约 -> 确认在列表 -> 挑选代理人 -> ...
```

### 过期邀约：邀约前必须先清

**昨天邀约了但没赴约，今天会被过期邀约卡住。** 会话里挂一个「已过期」卡片，
两个地方出红色感叹号：

| 位置 | 含义 | 实测坐标 |
|---|---|---|
| 顶部**中间（会话）tab 图标右上角** | 会话里有过期邀约 | (503,252)，tab 图标中心 (516,283) |
| 左侧角色列表**每项右上角** | 这个代理人有过期邀约 | x≈656，跟行 y 走 |

**顺序必须是：按 Q 唤出（默认就在会话 tab）→ 清过期邀约 → 点左边联系人列表。**
反过来先切列表会被卡住。

**判据绝不能只看红色。** 左栏头像本身就带红（猫又、红发角色），实测有
`x=415`、`x=404` 这类头像红点，按颜色一把抓会去点别人的行然后原地空转 ——
这是本次踩得最久的坑。判据要叠三层：

1. 区域限定：列表感叹号只在 `x 620-700`（行右上角）；
2. 尺寸：`w>=12 h>=14`、面积 `>=50`；
3. 形状：宽高比 `0.6~1.6`（实测真感叹号 w19 h20 ≈ 0.95，细长干扰条 5.0 被排掉）。

处理动作（实机验证）：点那一行（用感叹号 y + 30 落到行中心）→ 在会话里反复
推进（有白色选项条点第一条，没有就点对话区底部）→ 该行感叹号消失即算清完。
实测 2 个过期各 2~3 步就清掉，tab 红点随之消失。

**点掉一个不会重排列表**，所以按当前感叹号 y 逐行点；清不掉的记下 y 跳过，
继续清后面的，不能一失败就 break（否则会漏掉其他过期会话）。

### 选时段：四个方块全点一遍

邀约到「加入日程」这一步会弹时段面板。**不去识别当前选中哪个，直接四个全点，
最后点的那个就是最终时段。**

为什么这么干：时段是单选（选中态是黄底 + ✓ 角标），必须先选一个才能加入日程。
OCR 找「上午/下午/夜晚/凌晨」四个词不稳 —— 图标会被认成字，选中态文字变绿还会漏读。
坐标反而很稳：

```
面板蓝色框 (793,538)-(1482,811)
四个方块等宽，间距精确 168px，y 中心 665
  上午 (882,665) / 下午 (1050,665) / 夜晚 (1218,665) / 凌晨 (1386,665)
```

实测交叉验证：第 1 块黄底 bbox (813,615) 139x100 -> 中心 882；第 3、4 块深灰段
实测中心 1218、1386，与 882+168*n 完全吻合。

全点还有个好处：前几下点错也没关系，反正最后一下决定结果。

**「加入日程」不会被误当成 REPLY 选项**：它是深灰底黑字，纯白像素占比仅 0.86%，
过不了白条检测（实测 `_find_dialog_option` 在这个画面返回 None）。

### ⚠️ 根因：框架截图是 RGB，颜色判据必须按 BGR 用（2026-11-19 定案）

**这才是「过期邀约检测不到」的真正原因**，前面那节"界面重绘"只是次要因素。

现象：实机日志 `进入清理：列表感叹号 0 个，会话 tab 红点 False`，但画面上明明
挂着 3 个红色感叹号。

排查：同一帧画面用两种方式取图对比 ——

| 图源 | 按 BGR 解释 | 按 RGB 解释 |
|---|---|---|
| ImageGrab 直接抓屏（我排查时用的） | **3 个** | 0 个 |
| 控制器 screenshot()（插件实际用的） | 0 个 | **3 个** |

结论：**框架截图器返回的是 RGB**（`gdi_screencapper_base.py` 里 `COLOR_BGRA2RGB`，
bitblt 继承它所以一样）。框架内部 `find_character_avatars` / `template_info`
这些也按 RGB 写，这是框架约定。

但本插件的颜色常量（红色感叹号 HSV、白色选项条、tab 黄色高亮）是按 **BGR** 写的，
所以红蓝颠倒 —— 红色感叹号在数组里被当成"蓝色"，自然一个都检测不到。

**修法：覆写 `screenshot()`，统一 `COLOR_RGB2BGR` 后再交给下游。**
覆写一处比改 27 个调用点可靠，也不会动到共享框架。

验证：控制器截图转 BGR 后连续 5 帧稳定检出 3 个感叹号 + 徽标 True；
不转则 0 个。

**教训**：写颜色判据前先确认图源通道顺序。框架里 `cv2_utils` 自己也有两种写法
（`color_in_hsv_range` 用 BGR2HSV、`find_character_avatars` 用 RGB2HSV），
看代码容易被误导，**必须拿实机截图数像素确认**。

### 过期邀约检测不到：界面重绘时的时序坑（2026-11-19 实测暴露）


现象：日志显示 `清理过期邀约 -> 返回状态 已清理过期邀约`，但实际一个都没清，
后面直接去邀约代理人了。

**根因：点完 tab 界面会重绘，立刻截图抓到的是空列表。** 原来 `_clear_expired_invites`
第一次检测不到就 `break`，等于一帧空图直接让整个循环放弃。

修复三处：

1. **`_wait_list_settled`：连续采样取最大检出。**
   一开始我写成"相邻两次一致就提前返回"，但验证时暴露了更糟的问题：
   前两帧都还是空列表，长度都是 0 -> 判定"稳定" -> 返回空，后面画出来的
   感叹号完全没看到。**必须取整个采样过程中检出最多的那次**，不能靠"两次一致"。
2. **放宽检测区域余量。** tab 徽标实测 bbox `(493,240)-(514,264)`，原区域
   `(480,235,530,275)` 上边只留 5px，界面一抖就漏。放宽到 `(460,225,560,295)`；
   列表感叹号区域同步放宽到 `(616,320,700,910)`。
3. **加诊断日志。** 进节点先打印"列表感叹号 N 个 + tab 红点状态"；
   如果明明检出了却一个都没清，直接 `log.error` 报出来，下次不用猜。

验证：模拟"前 2 帧空、后 2 帧有数据"的重绘延迟 + 3 个过期邀约，
能全部清掉（3 次点击，剩余行空）。

### 次数用完：直接收工，不要继续试别人


今天 3 次用光后再点「邀约」，会弹「今天邀约次数已用完」+ 一个「确认」按钮。
**看到它就别再试其他人了**——每个都会弹同一个窗，纯浪费。

实测位置（1080p，OCR 读文字）：

```
提示文字「今天邀约次数已用完」中心 (960,524)
「确认」按钮文字中心 (978,626)   <- 在**画面中间**
绿色 ✓ 圆圈中心 (852,627)
```

⚠️ 这个按钮和信赖弹窗的右侧按钮 `(1129,647)` **不是一个位置**，别混用坐标。

两处收工判据，双保险：

1. **读「剩余邀约N/3」**：`N == 0` 就直接收工。这个更早、更省事——不用先点一次
   邀约去触发弹窗。实机确认 3 次用光后显示 `0/3`。
2. **识别弹窗**：万一是别的路径触发（比如从对话中弹出来），看到弹窗就点确认再收工。

收工时 `finish` 会先清残留弹窗再点右上角 X —— 弹窗会挡住关闭按钮。

### ⚠️ 两个弹窗长得很像，必须分开判（踩过的坑）


点「邀约」后会出两种弹窗，**判据绝不能混用**：

| | 满级弹窗 | 升阶弹窗 |
|---|---|---|
| 正文 | 和代理人已达到信赖等阶，是否继续发起邀约？ | 信赖已到达当前等阶满值，是否进行升阶事件？ |
| 副文 | 已达到最高信赖等阶，暂无法获得更多信赖 | 完成升阶事件后可继续提升信赖 |
| 按钮 | 取消 / **确认** | 取消 / **前往** |
| 处理 | 按配置决定取消或确认 | **只能取消** |

**升阶弹窗点「前往」会跳去升阶事件**，离开邀约流程、还可能改变角色状态。

踩的坑：起初用 `'信赖等阶'` 当判据，而升阶弹窗的正文是「信赖已到达当前等**阶**
满值」—— `find_by_lcs` 按**子序列**匹配（信赖…等…阶 顺序出现），于是误判成满级
弹窗，脚本接着点了「前往」。**`'信赖等阶'` 两个弹窗都有，绝对不能当判据。**

现在按各自专属词分开判，实测双向互斥：

```
满级专属：是否继续发起邀约 / 最高信赖 / 暂无法获得更多信赖
升阶专属：升阶事件 / 当前等阶满值 / 可继续提升信赖
```

代码里先判升阶（只点取消、直接返回「不继续」），再按开关处理满级。

### 信赖满级弹窗：两种做法按开关走

点「邀约」后如果这个代理人信赖满级，会弹「已达到信赖等阶，是否继续发起邀约？」。
**弹窗默认焦点在「确认」上** —— 误点会直接消耗一次邀约，所以必须先判弹窗。

按钮实测（1080p，OCR 读文字得到，与兜底坐标一致）：

| 按钮 | 文字中心 | 胶囊范围 |
|---|---|---|
| 取消 | (827,647) | x 620-910 |
| 确认 | (1129,647) | x 930-1220 |

**别用圆圈位置**：红色 X 圆心 (700,647)、绿色 ✓ 圆心 (1004,647)，都在按钮左端，
点在圆圈上会偏到按钮边缘。要点文字中心。

做法由配置 `continue_after_trust_full` 决定：

- **关**（默认）：点取消，换下一个代理人。信赖满级拿不到更多信赖值。
- **开**：点确认继续。信赖满级只是不再涨信赖值，邀约流程本身能走完。

### 尝试次数上限：`max_invite_attempts`（默认 5）

一天只能成功邀约 3 次，但**「尝试」和「成功」是两件事**。信赖全满、或卡着升阶
任务的角色点不动，只有成功次数上限的话，脚本会一路往下把列表上所有人都点一遍。

所以单独记一个 `invite_attempts`（点一次「邀约」就 +1，不管成没成），到上限就收手。
默认 5 次：比 3 次多两次余量，能跨过一两个点不动的人。

#### ⚠️ 光在一个节点检查没用（实机超限的教训）

实机日志出现 `第 5/5 → 6/5 → 7/5`，超了两次还在继续邀约。

原因：上限检查一开始只写在 `after_one_invite`，而那条路径只有**成功邀约后**才
会走到。信赖已满 / 升阶这类「跳过」走的是
`点击邀约 → 跳过换人 → 确认在列表 → 挑选代理人`，整条链完全不经过上限检查。

修法：**四个入口全设关卡**，任何一道命中就不再加人：

| 节点 | 作用 |
|---|---|
| `挑选代理人` | 挑人前就挡：尝试到顶 / 成功到顶 / 游戏里 0/3 |
| `点击邀约` | 硬闸门：节点 retry 重入时防重复点（实测到顶后点击数 0） |
| `跳过换人` | 跳过路径的关口（这次超限就漏在这） |
| `完成后换人` | 成功路径的关口 |

验证：模拟连续跳过 9 轮，第 5 次就返回「已扫描到上限」，不再出现 6/5、7/5。

**教训**：状态机里同一个约束要在**所有能走到它的入口**都检查一遍，
不能只挂在下游某一个节点上 —— 有几条绕行路径很容易漏。

配置在运行卡片上的齿轮里改（FLYOUT 弹窗，两项）。

### 二选一对话：点选项条，不是点 REPLY 标签

**`REPLY` 是选项组的标签（气泡图标 + 文字），点它没有任何反应。**
真正能点的是标签下方那几条**纯白圆角长条**。第一版就是点标签中心，结果脚本
在对话里空转、选不到任何选项。

选项条和白条对话气泡长得像，所以用三条互相独立的判据筛（会话区 760-1620 x 280-900）：

| 判据 | 选项条实测 | 对方气泡实测 | 阈值 |
|---|---|---|---|
| 宽度占会话区 | 0.79（678px） | 0.57（490px） | ≥ 0.68 |
| 中心 x 偏移占会话区 | 0.07（59px） | 0.17（145px） | ≤ 0.12 |
| 中心 y 位置占会话区 | 0.82 / 0.90 | 0.15~0.52 | ≥ 0.65 |

三条各自都能独立排掉气泡（已验证：构造"宽+居中+靠上"、"居中+靠下+窄"、
"宽+靠下+靠左" 三种对抗样本，分别被纵向 / 宽度 / 居中判据单独排掉）。
只用一条不够：卡太紧漏检真机白条，卡太松会去点别人的消息导致卡住。

**分辨率无关性**：框架已把截图统一缩到 1920x1080（`get_scaled_game_pos`
再按窗口宽高比放大回去），所以这些比例阈值对 2K 一样成立，比例量本身也不受
窗口尺寸影响。绝不写死绝对 y 坐标 —— 会话滚动位置会让它飘。

## 界面事实（这些是资产，别重测）

### 界面结构

### 结束状态与弹窗（都实机验过）
1. **普通邀约**：进对话 → 反复点白色选项条（不是 REPLY 标签）→ 出「开始邀约同行」。
2. **需选时段**：出「上午/下午/夜晚/凌晨 + 加入日程」。时段是单选（带 ✓ 角标），
   但**代码故意四个都点一遍**（坐标稳定，不用识别选中哪个），最后点的那个生效；
   再点「加入日程」，成功后对话出现 `[待办]xxx` + 「查看日程」。
3. **信赖两个弹窗**：满级弹窗按 `continue_after_trust_full` 决定取消还是确认；
   升阶弹窗**只点取消**。两者判据分开，见上面「两个弹窗长得很像」那一节。
